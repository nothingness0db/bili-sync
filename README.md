> 本仓库为 [amtoaer/bili-sync](https://github.com/amtoaer/bili-sync) 的 fork，在保留原视频同步能力的基础上，新增了 **动态同步、评论同步、账号与视频数据可视化、本地视频播放** 功能。

## 简介

bili-sync 是一款专为 NAS 用户编写的哔哩哔哩同步工具，由 Rust & Tokio 驱动。

除了同步视频（收藏夹 / 合集 / 投稿 / 稍后再看），本 fork 还支持：

- **UP 主动态同步**：图文、纯文字、转发、视频动态全类型抓取，正文、图片、点赞/评论/转发数一网打尽
- **评论同步**：评论队列独立抓取评论与楼中楼，按发布年龄定期复查，并补拉历史缺口
- **账号数据可视化**：粉丝数 / 关注数 / 投稿数 / 总播放数的历史折线图，名字 / 签名 / 头像的版本历史
- **逐视频数据与充电榜**：查看视频各项指标的历史趋势、增长，以及账号充电人数与历史榜单
- **本地视频播放**：在 Web UI 播放已下载的视频，支持分 P 选择、进度拖动与下载；B 站视频失效后仍可访问本地副本

## 视频浏览与播放

### 播放已下载的视频

1. 在 Web UI「视频」页找到视频，点击「详情」
2. 在详情页点击「播放本地视频」，打开播放器
3. 多分 P 视频可切换已下载的分 P，也可点击「下载此分 P」保存到本机

播放依赖服务器上仍存在的本地视频文件。使用 Docker 部署时，原下载目录需要继续挂载到容器内，且容器内路径与下载记录一致。B 站视频失效不影响已经保存的本地副本；尚未下载或文件已移除时，页面会提示没有可播放的本地文件。

浏览器能否直接播放取决于视频编码。若提示无法播放，可尝试「重新加载」，或下载后用本地播放器打开。

### 检查视频删除与失效

视频页的「检查删除/失效」会比对所选 UP 主的当前投稿列表，再逐条确认缺失或已失效的视频。支持全选、取消全选和单独选择；没有选择投稿源时不能开始检查。

「有效性」筛选将「失效」与「已删除」分开：确认删除的视频显示「已删除」及首次确认时间；其他不可用的视频显示「失效」。两类结果互不混入，本地文件和历史记录均保留。仅从投稿列表消失不会直接判定为删除，请求失败也不会被标记为删除。

### 查看视频统计与关联评论

- **视频详情**：展示该视频已采样的各项指标、历史趋势与范围内增长；「关联动态评论」中点击「查看评论」，在当前页面的弹窗内查看本地保存的动态正文、评论、楼中楼回复和图片。关闭弹窗后继续留在视频详情页
- **动态源详情 → 逐视频数据**：点击视频进入统计页，同样可以打开关联评论弹窗；点击「返回动态源详情」回到对应的动态源
- **返回视频列表**：从视频列表进入详情后，点击「返回视频列表」保留此前的筛选条件

关联评论来自本地同步的动态，需要先添加对应动态源并启用评论同步。没有关联动态或尚未同步评论时，页面会显示相应的空状态；弹窗展示本地已保存的数据，不会在打开时实时抓取 B 站评论。

## 动态同步使用说明

1. 在 Web UI「动态源」页点击「添加动态源」，填入 UP 主 ID（mid）与保存路径
2. 默认**不启用**，添加后打开「启用」开关
3. 可选项：「同步该 UP 主动态下的评论」——开启后自动拉取评论
4. 首次启用会全量拉取历史动态（按每轮任务限量处理，大 UP 可能需要多轮消化）
5. 之后每轮任务（默认 20 分钟）增量同步新动态

### 评论调度与任务优先级

任务按「新视频扫描与下载 → 动态和评论 → 视频统计与账号快照」执行。视频统计按 BV 号跨源复用最近一小时的数据，账号快照每小时检查一次。

开启动态源的评论同步后，首次处理时立即抓取；评论分页与楼中楼共用每条动态每轮 50 次请求预算，达到预算后原子保存评论和断点。独立队列每轮结束一分钟后继续消化，评论请求在新的视频下载任务开始时让出执行权。

| 发布后的时间 | 完整同步后的复查间隔 |
| --- | --- |
| 0～24 小时 | 1 小时 |
| 超过 24 小时～7 天 | 6 小时 |
| 超过 7 天～30 天 | 24 小时 |
| 超过 30 天 | 历史未抓取缺口、较新的视频评论计数表明有缺口（最多每天复查一次），或手动重扫 |

当热门接口声明的评论总数有缺口，或分页游标不再推进时，会使用完整列表接口补漏；补漏沿用同一请求预算和断点。置顶评论与其楼中楼也会保存。

间隔从上次完整扫描结束时间计算。未完成的分页继续使用断点，不受复查间隔限制。历史补拉先筛选实际缺口再限量入队，避免固定的前 50 条动态挡住较早的缺口。合作视频按评论区类型与对象 ID 串行抓取，多个动态保留各自的完整评论关联并复用仍在刷新周期内的同步结果。

评论只在对应动态源开启评论同步时自动抓取；仅添加投稿视频源不会自动开启评论同步。首次导入的较老动态按已知评论缺口逐批补拉。

账号视频计数排除详情接口明确返回已删除或不可见的历史动态视频，不会因一条失效稿件跳过整个账号快照。不可见（`62002`）每 24 小时复查恢复，确认删除（`-404` / `62012`）停止自动采样；本地文件与历史统计均保留。网络等请求失败仍会跳过本次账号计数快照，日志列出无法确认的 BV 号。

### 动态落盘结构

```
{保存路径}/
├── {发布日期} {动态id}/          # 例：2026-08-07 1233953656171134977/
│   ├── dynamic.json             # 原始接口数据（完整保留）
│   ├── content.md               # 渲染正文（含转发内容）
│   ├── pics/01.jpg              # 动态图片
│   └── comments/
│       ├── comments.json        # 全部评论（含楼中楼）结构化数据
│       ├── comments.md          # 评论渲染
│       └── {rpid}_1.jpg         # 评论图片
```

### 数据存储

| 表 | 内容 |
|---|---|
| `dynamic_source` | 动态源（UP 主 + 路径 + 开关）|
| `dynamic` | 动态本体（正文 / 类型 / 统计 / 原始 JSON）|
| `reply` | 评论（含楼中楼层级）|
| `upper_stat` | 账号数据快照（粉丝 / 关注 / 投稿 / 播放 + 名字 / 签名 / 头像）|
| `video_stat` | 按 BV 号保存逐视频统计快照（播放 / 点赞 / 投币 / 收藏 / 分享 / 评论 / 弹幕），指标分别落列 |
| `video_stat_source` | 保存账号与 BV 号的关联，合作视频在多个账号中共享同一份统计历史 |
| `elec_stat` | 每次账号同步的充电展示状态、累计人数及采样时间 |
| `elec_rank` | 每次充电快照返回的榜单成员、UID、姓名、头像和名次 |

账号详情页新增「逐视频数据」，包含普通投稿与动态视频；点进视频可查看各项指标的当前值、趋势和记录期间增长。已有下载视频的详情页也展示这些数据。

每轮同步持续采样已知视频，不只采集新视频。视频源中同一 BV 号在同一轮复用已获取的详情；动态源合并当前投稿与本地 AV 动态，逐个采样。数值不变也保存快照，缺失或隐藏的指标保留为 NULL，失败不写入零值。采样沿用原有 BiliClient、凭据与 WBI 签名，新增采样请求全局串行并保持 400ms 间隔，遇到风控终止本轮。

增长按所选范围内实际首末采样计算，只有一个点或缺少指标时显示暂无增长数据。原始快照全部保留；长时间跨度的图表抽取约 1000 个点并保留首末点。历史动态补齐 `video_bvid` 关联，可通过 `video_stat.bvid = dynamic.video_bvid`、`dynamic.id = reply.dynamic_id` 联查统计与评论；升级时不会把旧 JSON 中的值伪装成历史采样。

充电榜通过官方 `x/space/wbi/acc/info` 的 `data.elec.show_info` 采样，沿用原有 Cookie、WBI 签名和限流。每次定时账号同步及手动扫描都保留快照，账号数据不变也记录；账号页支持人数趋势、历史榜单及相邻采样的进出榜与名次变化。请求失败或榜单未展示不会被记录为全员掉榜，成员与快照在同一个事务中保存。

`total` 是累计充过电的人数，榜单仅包含接口返回的 Top 成员，不是全部活跃用户。进出榜不能证明续费或停充，接口也不提供金额或流水。关闭/隐藏或缺失榜单时标记为不可观察；明确开放但无榜（state=1）可保存空榜。升级前没有采样的历史不补造。

## 升级与迁移（自原版本）

从原版 amtoaer/bili-sync 升级到本 fork **无需任何手动操作**：

1. 替换二进制文件，重启程序
2. 启动时数据库自动增量迁移：新增动态、评论、账号与视频快照表，并补齐相关列与索引
3. 原有配置（auth token、凭据、视频源、收藏夹、下载记录）全部保留
4. 视频下载功能完全不受影响
5. 动态同步默认关闭，在 Web UI「动态源」页添加 UP 主后启用

## 风控与限流须知（重要）

B 站对接口存在冷却型风控（`-403` 访问权限不足，IP 级，触发后几十分钟到 1 小时自动解除）。本项目已内置多重防护：

- 动态列表接口：每页请求间隔 250ms
- 评论接口：每次请求间隔 400ms（该接口为风控高发点，务必保持）
- 评论请求预算：每条动态每轮最多 50 次请求，顶级评论与楼中楼共用预算；逐页保存断点，下轮继续，程序重启后也可恢复
- 重扫队列：优先处理尚未尝试的动态，达到预算或失败的任务轮到队尾，避免阻塞历史积压
- 每轮任务处理上限：新动态 20 条 / 重扫评论 5 条（防止首次全量导入时请求过快）
- 全局请求限流器：每 250ms 最多 4 个请求
- 触发风控后自动终止本轮任务，等待下一轮，不继续请求

日常增量使用（每轮约 5-10 个请求）远低于风控阈值，无需干预；请勿手动频繁触发任务或大量重扫。

## 常见问题（FAQ）

**Q: 遇到 `-403 访问权限不足` 怎么办？**
A: 这是冷却型风控，等待 30 分钟 ~ 1 小时会自动解除。程序检测到风控会自动终止本轮任务，下一轮自动重试，无需干预。期间不要频繁手动触发任务，也不要用"换登录凭据"硬试——风控针对 IP，换凭据无效。

**Q: 首次添加大 UP 主，动态处理很慢？**
A: 每轮任务限量处理新动态，较大的历史档案需要分批消化。开启评论同步的动态源还有独立队列：每轮处理结束一分钟后继续，并保留评论分页断点；视频下载任务优先执行。

**Q: 评论多久复查一次？**
A: 首次处理时立即抓取；发布后首日每小时、第 2～7 天每 6 小时、第 8～30 天每 24 小时复查。超过 30 天按已知缺口、更新的视频评论计数或手动要求触发。分页未完成时继续断点，不必等待复查间隔。

**Q: 动态和评论的图片在哪看？**
A: Web UI 动态详情弹窗内直接查看；本地文件在动态目录的 `pics/` 与 `comments/` 下。

**Q: 为什么不把动态做成 nfo / 媒体库格式？**
A: 媒体服务器（Jellyfin / Emby / Infuse）只识别视频内容，不识别动态。动态以 JSON + Markdown 落盘（`dynamic.json` / `content.md`），正文、评论、图片在 Web UI 与文件系统中均可查看。

## 从源码构建

在仓库根目录执行，先构建前端，再构建后端。前端产物 `web/build` 会嵌入后端二进制；修改前端后，需要重新构建前端和后端，并替换运行中的二进制或容器镜像。

```bash
# 前端
cd web
npm ci --legacy-peer-deps
npm run build
cd ..

# 后端（使用 rust-toolchain.toml 指定的 Rust 工具链）
cargo build --release
```

构建后的程序位于 `target/release/bili-sync-rs`。

前端检查与测试（在 `web` 目录执行）：

```bash
npm run check
npm run lint
npm test
```
