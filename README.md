## 简介

bili-sync 是一款专为 NAS 用户编写的哔哩哔哩同步工具，由 Rust & Tokio 驱动。

除了同步视频（收藏夹 / 合集 / 投稿 / 稍后再看），本 fork 还支持：

- **UP 主动态同步**：图文、纯文字、转发、视频动态全类型抓取，正文、图片、点赞/评论/转发数一网打尽
- **评论同步**：动态发布后 5 天内自动同步评论（含楼中楼），5 天外可手动重扫（慢任务分批，避免触发风控）
- **账号数据可视化**：粉丝数 / 关注数 / 投稿数 / 总播放数的历史折线图，名字 / 签名 / 头像的版本历史

## 功能

- [x] 动态源管理：Web UI 添加 / 编辑 / 删除 UP 主动态源

- [x] 评论同步：动态发布后 5 天内每轮自动更新评论与楼中楼
- [x] 手动重扫：单条动态或全部动态的评论重新同步（慢任务，每轮限量处理）
- [x] 账号数据快照：粉丝 / 关注 / 投稿 / 播放数，有变化才记录

- [x] Web UI 浏览动态正文、图片与评论树

## 动态同步使用说明

1. 在 Web UI「动态源」页点击「添加动态源」，填入 UP 主 ID（mid）与保存路径
2. 默认**不启用**，添加后打开「启用」开关
3. 可选项：「同步该 UP 主动态下的评论」——开启后自动拉取评论
4. 首次启用会全量拉取历史动态（按每轮任务限量处理，大 UP 可能需要多轮消化）
5. 之后每轮任务（默认 20 分钟）增量同步新动态

### 动态落盘结构

```
{保存路径}/
├── {发布日期} {动态id}/          # 例：2026-08-07 1233953656171134977/
│   ├── dynamic.json             # 原始接口数据（完整保留）
│   ├── content.md               # 渲染正文（含转发内容）
│   ├── pics/01.jpg              # 动态图片
│   └── comments/
│       ├── comments.json        # 全部评论（含楼中楼）结构化数据
│       ├── comments.md          # 评论渲染
│       └── {rpid}_1.jpg         # 评论图片
```

### 数据存储

| 表 | 内容 |
|---|---|
| `dynamic_source` | 动态源（UP 主 + 路径 + 开关）|
| `dynamic` | 动态本体（正文 / 类型 / 统计 / 原始 JSON）|
| `reply` | 评论（含楼中楼层级）|
| `upper_stat` | 账号数据快照（粉丝 / 关注 / 投稿 / 播放 + 名字 / 签名 / 头像）|
| `video_stat` | 按 BV 号保存逐视频统计快照（播放 / 点赞 / 投币 / 收藏 / 分享 / 评论 / 弹幕），指标分别落列 |
| `video_stat_source` | 保存账号与 BV 号的关联，合作视频在多个账号中共享同一份统计历史 |
| `elec_stat` | 每次账号同步的充电展示状态、累计人数及采样时间 |
| `elec_rank` | 每次充电快照返回的榜单成员、UID、姓名、头像和名次 |

账号详情页新增「逐视频数据」，包含普通投稿与动态视频；点进视频可查看各项指标的当前值、趋势和记录期间增长。已有下载视频的详情页也展示这些数据。

每轮同步持续采样已知视频，不只采集新视频。视频源中同一 BV 号在同一轮复用已获取的详情；动态源合并当前投稿与本地 AV 动态，逐个采样。数值不变也保存快照，缺失或隐藏的指标保留为 NULL，失败不写入零值。采样沿用原有 BiliClient、凭据与 WBI 签名，新增采样请求全局串行并保持 400ms 间隔，遇到风控终止本轮。

增长按所选范围内实际首末采样计算，只有一个点或缺少指标时显示暂无增长数据。原始快照全部保留；长时间跨度的图表抽取约 1000 个点并保留首末点。历史动态补齐 `video_bvid` 关联，可通过 `video_stat.bvid = dynamic.video_bvid`、`dynamic.id = reply.dynamic_id` 联查统计与评论；升级时不会把旧 JSON 中的值伪装成历史采样。

充电榜通过官方 `x/space/wbi/acc/info` 的 `data.elec.show_info` 采样，沿用原有 Cookie、WBI 签名和限流。每次定时账号同步及手动扫描都保留快照，账号数据不变也记录；账号页支持人数趋势、历史榜单及相邻采样的进出榜与名次变化。请求失败或榜单未展示不会被记录为全员掉榜，成员与快照在同一个事务中保存。

`total` 是累计充过电的人数，榜单仅包含接口返回的 Top 成员，不是全部活跃用户。进出榜不能证明续费或停充，接口也不提供金额或流水。关闭/隐藏或缺失榜单时标记为不可观察；明确开放但无榜（state=1）可保存空榜。升级前没有采样的历史不补造。

## 升级与迁移（自原版本）

从原版 amtoaer/bili-sync 升级到本 fork **无需任何手动操作**：

1. 替换二进制文件，重启程序
2. 启动时数据库自动增量迁移：新增动态、评论、账号与视频快照表，并补齐相关列与索引
3. 原有配置（auth token、凭据、视频源、收藏夹、下载记录）全部保留
4. 视频下载功能完全不受影响
5. 动态同步默认关闭，在 Web UI「动态源」页添加 UP 主后启用

## 风控与限流须知（重要）

B 站对接口存在冷却型风控（`-403` 访问权限不足，IP 级，触发后几十分钟到 1 小时自动解除）。本项目已内置多重防护：

- 动态列表接口：每页请求间隔 250ms
- 评论接口：每次请求间隔 400ms（该接口为风控高发点，务必保持）
- 评论请求预算：每条动态每轮最多 50 次请求，顶级评论与楼中楼共用预算；逐页保存断点，下轮继续，程序重启后也可恢复
- 重扫队列：优先处理尚未尝试的动态，达到预算或失败的任务轮到队尾，避免阻塞历史积压
- 每轮任务处理上限：新动态 20 条 / 重扫评论 5 条（防止首次全量导入时请求过快）
- 全局请求限流器：每 250ms 最多 4 个请求
- 触发风控后自动终止本轮任务，等待下一轮，不继续请求

日常增量使用（每轮约 5-10 个请求）远低于风控阈值，无需干预；请勿手动频繁触发任务或大量重扫。

## 常见问题（FAQ）

**Q: 遇到 `-403 访问权限不足` 怎么办？**
A: 这是冷却型风控，等待 30 分钟 ~ 1 小时会自动解除。程序检测到风控会自动终止本轮任务，下一轮自动重试，无需干预。期间不要频繁手动触发任务，也不要用"换登录凭据"硬试——风控针对 IP，换凭据无效。

**Q: 首次添加大 UP 主，动态处理很慢？**
A: 每轮任务限量处理（新动态 20 条/轮），大 UP 的全量历史动态需要多轮消化（每轮 20 分钟）。这是防风控的刻意设计，首次全量导入的请求量远低于风控阈值，只是慢。

**Q: 动态评论为什么只自动同步 5 天？**
A: 动态发布后 5 天内，每轮任务都会自动更新评论（新评论会持续出现）。5 天后评论基本稳定，改为手动触发：在动态详情页点击「重扫该动态的评论」或「全部重扫评论」。

**Q: 动态和评论的图片在哪看？**
A: Web UI 动态详情弹窗内直接查看；本地文件在动态目录的 `pics/` 与 `comments/` 下。

**Q: 为什么不把动态做成 nfo / 媒体库格式？**
A: 媒体服务器（Jellyfin / Emby / Infuse）只识别视频内容，不识别动态。动态以 JSON + Markdown 落盘（`dynamic.json` / `content.md`），正文、评论、图片在 Web UI 与文件系统中均可查看。

## 从源码构建

```bash
# 后端
cargo build --release

# 前端（构建产物嵌入后端二进制，改动前端后需重新构建后端）
cd web
npm install --legacy-peer-deps
npm run build
cd ..
cargo build --release
```

前端类型检查：`cd web && npm run check`
